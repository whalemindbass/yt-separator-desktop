# 베이스 자동 채보 — 실험실

앱에 들어 있는 채보 기능(`renderer/workers/tab-*.js`)을 재고 고치는 자리다.
기능 자체는 화면에서 숨겨져 있다 — 되살리려면 `renderer/index.html` 의 `hidden` 두 개를 지운다.

## 왜 이 폴더가 있나

정답지는 이 프로젝트에서 가장 비싼 물건이다. 617개 음을 손으로 맞춰 넣은 것이고,
잃으면 며칠이 사라진다. 그런데 지금까지 정답지도 채점 도구도 임시 폴더에 있었다.
채점 한 번 하려면 HTML 을 `renderer/` 에 복사하고 URL 을 손으로 조립해야 했다.
그 마찰이 "재보지 않고 고치는" 습관을 만들었고, 실제로 한 번은 순환 측정으로
개선이 아닌 것을 개선이라고 판단했다(ARCHITECTURE.md 의 막다른 길 표를 보라).

## 재는 법

```
npm run lab                 도구 목록과 기준선
npm run lab -- onsets       손 정답지 대비 온셋 채점   ← 시각·놓침·헛노트는 이것으로만 잰다
npm run lab -- score        탭 악보 정답지 대비 채점   ← 음정은 이것으로 잰다
npm run lab -- onsets-synth 합성 음원 대조 (정답이 정확히 알려진 것)
npm run lab -- annotate     온셋을 손으로 표기 (창이 뜬다)
npm run lab -- dump         마디 악보 덤프
npm run lab -- notes        검출된 노트 목록
```

**정답지가 두 개고 각각 잴 수 있는 것이 다르다.** 탭 악보는 음정만, 손 온셋은 시각만이다.
왜 그런지는 아래 두 절에 있다. 섞어 읽으면 없는 개선을 봤다고 하게 된다.

오프스크린 Electron 에서 돌고 결과가 터미널에 그대로 나온다. 창을 열 필요가 없다.

**무엇을 바꾸든 `npm run lab -- score` 를 먼저 돌려 지금 값을 적어 두고, 고친 뒤 다시 돌린다.**
숫자가 나아지지 않으면 그 변경은 개선이 아니다.

## 필요한 파일

오디오는 저작권이 있어 저장소에 없다. `manifest.json` 에 무엇이 어디 있어야 하는지 적혀 있다.

- `bass_sample.wav` — 저장소 루트 (분리된 베이스 스템, 210초)
- 드럼·기타·보컬 스템 — `%APPDATA%/yt-separator-desktop/downloads/stems/`

## 필요한 파일 (이어서)

- `ground-truth/bass_sample.onsets.txt` — 손으로 찍은 온셋 670개. **이건 저장소에 있다.**
  잃으면 다시 만드는 데 몇 시간이 든다.

## 지금 서 있는 자리

음정 (탭 악보 정답지 617음 · `npm run lab -- score`):

```
YIN   검출 690 · 일치 547 (89%) · 음정오류 39 · 놓침 31 · 옥타브 무시 90%
basic-pitch  4%  (옥타브 무시 6%)
```

시각 (손 온셋 정답지 670개 · 밀림 보정 후 허용오차 50ms · `npm run lab -- onsets`):

```
YIN   일치 573 · 놓침 97 · 잉여 117 · F1 84%
```

`score` 가 내놓는 **잉여는 읽지 마라.** 그 정답지는 옛 검출기 출력에서 파생돼 그때의
잉여를 0 으로 고정해 두었다 — 새로 찾은 음은 옳든 그르든 전부 잉여로 세어진다.
헛노트를 세려면 `onsets` 를 봐야 한다.

## 87% 는 무엇이었나 — 그리고 정답지를 믿을 수 있는 범위

문서에 적힌 **87% · 잉여 0** 은 코드를 돌린 값이 아니었다. 저장된 덤프 파일
(`ground-truth/bass_sample.raw-dump.txt`, 580음)을 채점한 값이다. 그 파일을 지금 채점하면
`일치 539(87%) · 음정오류 41 · 놓침 37 · 잉여 0` 으로 문서와 맞는다. 코드는 그때와 동일하다.

그런데 그 과정에서 더 중요한 것이 나왔다.

**정답지는 그 덤프에서 파생됐다.** 덤프 580음의 시각이 정답지에 100% 그대로 들어 있다(오차 1ms 이내).
사람이 한 일은 빠진 37음을 더하고 음정 41개를 고친 것이다. 시각은 검출기가 정한 그대로다.

그래서:

- **"잉여 0" 은 품질이 아니라 구조적 보장이었다.** 검출기가 찾은 음이 전부 정답지에 그 시각으로
  들어 있으니 헛 노트가 나올 수가 없다.
- **타이밍·온셋 정확도는 이 정답지로 잴 수 없다.** 580음에 대해 검출기는 정의상 틀릴 수 없다.
- **음정 정확도는 잴 수 있다.** 라벨을 손으로 고쳤기 때문이다.

앞서 한 번 순환 측정에 속은 적이 있는데(막다른 길 표의 "운지 습관 2패스"), 이번 것은 토대에 있었다.
**온셋·타이밍·헛노트에 관한 개선은 지금 정답지로 판정할 수 없다.**

## 벽이 어디인가

두 종류의 결함이 남아 있고, 원인이 서로 다르다.

| 결함 | 수 | 성격 |
|---|---|---|
| 음정 오류 | 39 | 옥타브·5도 혼동. 음정 클래스는 맞다(90% vs 89%) |
| 놓친 음 | 97 | 손 정답지 기준. 여전히 같은 음을 다시 튕긴 자리가 많다 |
| 헛 노트 | 117 | 손 정답지 기준. 분리 아티팩트가 이 특징에서 온셋과 같은 모양이다 |

놓친 음의 절반은 온셋 창을 고쳐 되찾았다(182 → 97, 6번 절). 남은 것은
**분리 과정에서 어택이 뭉개진 자리**로 보인다. 스템만 보고는 되찾을 수 없을 가능성이 크고,
그렇다면 답은 다른 신호이거나 더 깨끗한 분리다. 이 가름은 MIDI 정답으로만 지을 수 있다.

## 합성 음원으로 알아낸 것 (2026-08-13)

`npm run lab -- synth` 로 만든 73초 · 156음짜리 베이스는 시각·음정을 우리가 정했으므로
검출기와 무관하다. 같은 음 반복을 90쌍 넣어 지금의 실패 모드를 정면으로 겨눴다.

**1. 깨끗한 신호에서도 반복 타현을 놓친다.**

```
YIN (기본값)  일치 97 (62%) · 놓침 53 · 잉여 13
  놓친 53음 중 직전과 같은 음정이 49 · 직전과 0.2초 이내가 45
```

분리를 전혀 거치지 않았는데도 그렇다. 그리고 신호에는 증거가 있다 —
정답 온셋 앞뒤 20ms 에너지비를 재면 **빠른 반복 45곳 전부 20% 이상 상승**, 중앙값 +66% 다.
`lab/tab/tools/` 의 검사로 확인했다.

**2. 그런데 임계값을 낮추는 것이 답은 아니다.**

```
합성(깨끗한 신호)     0.08 → 0.02   +31음 · 잉여 13 → 10   (오히려 준다)
실제 곡(분리 스템)    0.08 → 0.02   +22음 · 잉여 26 → 264  (폭증)
```

같은 변경이 정반대로 작용한다. **`onsetThresh: 0.08` 은 분리 스템의 잡음 바닥이 강요한 값이다.**
깨끗한 신호에서는 그 값이 31음을 헛되이 버리고, 스템에서는 낮추는 순간 아티팩트가 쏟아진다.

막다른 길 표의 "임계값 낮추기 = 1음당 잔음 6개" 는 실제 곡에 대해서는 방향이 맞았다.
다만 그것이 **검출기의 한계인지 입력의 한계인지** 구분할 방법이 없었을 뿐이다. 이제 있다.

**3. 그래서 다음 질문이 뾰족해졌다.**

- 깨끗한 신호에서도 임계값을 최대한 낮춰야 83% 다. 남은 20음은 임계값이 아니라 **분절**의 문제다.
- 스템에서 임계값을 낮출 수 있으려면 잡음 바닥이 내려가야 한다 — 분리 후처리, 또는 다른 분리 모델.
**4. 국소 적응 임계값 — 해봤고, 아니었다.**

`median + k·MAD` 로 그 자리의 flux 변동폭에 맞춰 여유를 정하도록 만들었다
(`onsetAdaptive` 옵션, 기본 꺼짐).

```
합성   k 1.5   82%  잉여 14      (고정 0.02 의 82% · 잉여 10 과 비슷)
실제   k 1.5   90%  잉여 414     (고정 0.02 는 89% · 잉여 264)
실제   k 4.0   89%  잉여 352
```

깨끗한 신호에서는 최적 고정값과 비슷하고, **스템에서는 더 나쁘다.** 이유는 분명하다 —
잡음 구간에서는 MAD 도 작아지므로 문턱이 잡음을 따라 내려간다. 고정 여유값이 오히려
그것을 막고 있었다. `onsetFloor` 를 올리면 고정 방식으로 되돌아갈 뿐이다.

그래서 남는 결론: **분리 스템에서는 이 특징(로그 에너지 플럭스) 위의 어떤 문턱 정책도 안 된다.**
아티팩트가 이 특징에서 온셋과 같은 모양이기 때문이다. 문턱이 아니라 **특징 자체가 한계**다.
다음은 다른 특징(저역 대역별 스펙트럴 플럭스, 학습된 온셋)이거나 더 깨끗한 입력이다.

**5. 온셋용 에너지 창 — 원인을 찾았다. (판정은 6번에서 뒤집힌다)**

온셋 검출이 쓰는 RMS 가 **YIN 의 피치 창(N=2048, 약 93ms)과 같은 것**이었다. 그 창은 저음 한 주기를
담으려고 그만큼 긴 것인데, 어택은 5~20ms 짜리 사건이다. 93ms 로 평균 내면 150ms 간격 반복의
상승(20ms 창 에너지비 1.66)이 남지 않는다. 문턱을 아무리 만져도 없는 봉우리는 못 찾는다.

짧은 창을 따로 두고(`onsetWinMs`) 창 × 문턱을 훑었다.

```
합성 (정답 독립)                     실제 스템 (정답이 검출기에서 파생)
창\문턱   0.08      0.18             창\문턱   0.08       0.18
피치창   62%/ 13   46%/ 13           피치창   86%/  26   83%/   3
20ms     88%/ 12   83%/ 12           20ms     89%/ 156   88%/  83
46ms     75%/ 12   55%/ 12           46ms     88%/ 129   87%/  33
```

**합성에서는 20ms 가 62% → 88%, 잉여는 오히려 하나 준다.** 0.08~0.12 구간이 평평해 아슬아슬한
튜닝도 아니다. 그런데 **스템에서는 +3%p 를 얻는 대신 잉여가 26 → 156 으로 뛴다.**

여기서 판단이 막힌다. 믿을 수 있는 잣대(합성)는 짧은 창이 옳다고 하고, 제품이 실제로 도는
입력의 잉여 수치는 믿을 수 없다. 6배를 전부 정답지 편향으로 돌리기도 어렵다.
**그래서 기본값은 옛 동작(`onsetWinMs: 0`)으로 두었다.** 원인과 표는 남긴다.

이 교착은 다음 과제가 무엇인지 정확히 가리킨다 — **실제 곡의 독립 정답지**. 그것 없이는
이 표의 오른쪽 절반을 읽을 수 없고, 읽을 수 없으면 고를 수 없다.

## 6. 독립 정답지를 만들었고, 5번의 판정이 뒤집혔다 (2026-08-13)

`npm run lab -- annotate` 로 210초 전체의 온셋을 손으로 찍었다 — 670개.
표기 도구는 `tab-core` 를 import 하지 않는다. 화면에 검출 결과를 띄우지도 않는다.
그래서 검출기와 무관하다.

**먼저 이 정답지 자체를 검사했다** (`tools/onsetcheck.py`, `tools/align.py`).
비싼 물건일수록 쓰기 전에 재야 한다는 것을 여기서 이미 두 번 배웠다.

- 역행 0 · 중복 0 · 30초 구간마다 초당 2.0~3.9개로 고르다 (앞부분만 하다 만 것이 아니다)
- 오디오의 실제 에너지 상승 지점보다 **약 50ms 늦다.** 사람이 찍으면 그렇게 된다.
  상수라서 채점할 때 밀림 보정으로 걷어낸다.
- 검출기 덤프와 **어긋난 방향이 반대다.** 파생된 정답지는 이런 모양이 나올 수 없다.

그리고 5번의 표를 다시 그렸다. 밀림을 보정한 뒤, 허용오차 50ms:

```
실제 곡 (손 정답지 670 · 일치/놓침/잉여 F1)          합성 (정답 정확)
창\문턱      0.08              0.12                 밀림 / 흔들림(IQR)
피치창   488/182/112 77%   478/192/ 89 77%         -39ms / 38ms
20ms     568/102/177 80%   573/ 97/117 84%          -9ms /  7ms
46ms     565/105/146 82%   556/114/ 90 84%
```

**5번에서 적용을 막았던 "스템에서 잉여가 26 → 156 으로 뛴다" 는 허수였다.**
그 잉여는 검출기에서 파생된 정답지가 만든 것이다 — 짧은 창이 새로 찾아낸 음은
옳든 그르든 전부 잉여로 세어졌다. 진짜로 재면 짧은 창은 **놓침과 잉여를 함께 줄인다.**

**밀림도 같은 원인이었다.** 93ms 피치 창은 어택을 평균으로 뭉개면서 시각까지 39ms 앞으로
당기고 있었다. 상수 보정을 넣을 뻔했는데 처방이 틀린 것이었다 — 창을 20ms 로 줄이니
밀림 39ms → 9ms, 흔들림 38ms → 7ms 로 저절로 사라졌다.

그래서 기본값을 바꿨다: **`onsetWinMs: 20` · `onsetThresh: 0.12`.**
독립된 두 잣대(손 정답지, 합성 음원)가 같은 칸을 가리켰다.

곁가지로 얻은 것: 음정도 **86% → 89%**, 음정오류 45 → 39, 놓침 43 → 31 로 올랐다.
온셋을 제대로 찾으면 분절이 맞고, 분절이 맞으면 피치 추정이 깨끗한 구간을 본다.

### 여기서 배운 것

세 번 같은 실패를 했다. 운지 습관 2패스(순환 측정), 87% 문서값(덤프 채점),
그리고 이번의 "잉여 156"(파생 정답지). 전부 **잣대를 재지 않고 결과를 읽은 것**이다.
`tools/onsetcheck.py` 와 `align.py` 는 그래서 남긴다 — 다음 정답지도 쓰기 전에 저걸 통과해야 한다.

## 7. 프렛 배치와 디스코 옥타브 주법 (2026-08-13)

여기까지는 전부 **검출**을 재고 있었다. 그런데 제품의 값은 배치에 있다 —
음정이 맞아도 사람이 짚을 수 없으면 못 쓰는 악보다. 그것을 한 번도 안 쟀었다.

### 연주 가능성은 정답지가 필요 없다

물리 제약이라 (시각, 현, 프렛) 셋만 있으면 판정된다. 순환의 위험이 없다.
`npm run lab -- playable` 이 네 가지를 낸다 — 시간 안에 못 가는 자리 이동 · 같은 음이
여러 자리로 흩어진 정도 · 12프렛 위 비율 · 손이 옮겨 다닌 횟수.

첫 측정에서 나온 것: **자리 이동은 문제가 아니었다**(불가 0회). 문제는 흩어짐이었다.

```
midi 41 (F2)  E현13 x18 · D현3 x56     같은 음이 10프렛 떨어진 두 자리
midi 45 (A2)  E현17 x5 · D현12 x8 · G현2 x29
```

원인은 `assignFrets` 의 비용 계산이었다:

```
A2 를 어디에 둘 것인가    E현17  0.02x17 + 0.50x0 = 0.34   <- 이겼다
                          A현12  0.02x12 + 0.50x1 = 0.74
```

`LOW_STRING = 0.50`(굵은 현 선호)이 `POS_COST = 0.02`(프렛 높이)를 압도해서 전부 E현으로
몰아 17프렛까지 기어올라갔다. 굵은 현 선호를 0.12 로 내리고, 프렛 높이에 꺾임점을 두었다
(7프렛까지 거의 공짜, 그 위로 프렛당 0.10 — 5와 7의 차이는 사람에게 없고 12와 17은 크다).

```
lowString/highRate   불가   흩어짐(음정/노트)  12프렛위   이동
0.50 / 0    (옛)      0        11/367           8.4%      70
0.12 / 0.10 (새)      0         7/283           2.5%      21
```

### 두 번째 곡 — 디스코 옥타브 주법

`bass_sample_2.wav` (240초, 분리 스템). 근음과 그 한 옥타브 위를 번갈아 치는 곡이다.

정답지는 `tools/octave.py` 가 배음렬 점수로 뽑았다 — YIN 과 방식이 달라 독립이고,
만들 때 무작위 40개를 스펙트럼으로 되짚어 39/40 을 확인했다. 787음 · 옥타브 도약 324회 ·
**옥타브 위쪽 음은 길이 중앙 90ms.**

첫 측정: 옥타브 위쪽 음 226개 중 맞춘 것 **32개(14%)**. 나머지 음은 85%.

여기서 가설을 두 번 세우고 두 번 다 측정에 부정당했다. 남겨 둘 값어치가 있다.

1. **"옥타브 판정 문턱(`octRatio`) 이 낮아서 접힌다"** → 0.55 부터 1.6 까지 훑어도
   32 → 34 로 꿈쩍하지 않았다.
2. **"온셋 특징이 로그 에너지 플럭스라, 에너지가 대역만 옮겨가는 옥타브 타현이 안 보인다"**
   → 대역별 스펙트럴 플럭스를 따로 재봤다(`tools/fluxprobe.py`). 헛노트 5% 문턱에서
   에너지 플럭스 7.1% vs 스펙트럴 플럭스 8.4%. **둘 다 못 잡는다.** 특징 문제가 아니었다.

답은 코드에 있었다. 옥타브 검사에 **아래로 접는 길만 있고 위로 올리는 길이 없다.**
낮은 음이 울리는 중에 그 옥타브를 치면 잔향의 주기가 남아 YIN 이 낮은 쪽을 물고,
그것을 되돌릴 방법이 없었다. 그래서 "놓침 160" 은 진짜 놓침이 아니라 **음 경계조차 생기지
않은 접힘**이었다 — 160 + 28 = 188 이 한 원인이다.

가르는 표는 스펙트럼이 이미 알려줬다:

```
진짜  58Hz  h1 1.00 · h2 0.66 · h3 0.43     h3/h2 0.65 · h2/h1 0.66
진짜 115Hz  h1 0.11 · h2 1.00 · h3 0.00     h3/h2 0.00 · h2/h1 9.0
```

hz 가 진짜 기본파면 3배음이 서 있고, 진짜가 2·hz 라면 3·hz 는 그것의 1.5배라 배음이 아니어서
비어 있다. 조건을 하나만 두면(3배음만) 원래 배음이 약한 음까지 올려버려 **샘플1 이 89% → 78%**
로 무너졌다. 기본파가 죽어 있다는 두 번째 조건을 붙이니 그 회귀가 사라졌다.

두 곡 격자 훑기로 골랐다 (`octUpRatio` × `octUpH2`):

```
up / h2      샘플1 음정   샘플2 옥타브위   샘플2 나머지
0    (옛)       89%          14%            85%
0.25 / 1.2      88%          61%            88%
0.35 / 1.0      88%          69%            88%     <- 채택
0.5  / 1.2      83%          64%            88%
0.7  / 1.2      50%          62%            88%
```

한 곡만 봤으면 0.7 도 괜찮아 보였을 것이다. **두 곡을 같이 훑지 않았으면 골랐을 값이다.**

### 남은 것

- 흩어짐은 줄었지만 사라지지 않았다(샘플1 9/24 · 샘플2 8/24). DP 가 국소 연결만 최적화해서
  한 번 자리를 옮기면 되돌아오지 않는다. 곡 전체 차원의 자리 선호(2패스 또는 전역 닻)가 필요하다.
- 샘플1 의 "시간 안에 못 가는 이동" 이 0 → 2 회로 늘었다. 검출된 음이 늘어난 대가다.
- 샘플2 는 옥타브 위쪽 음 31% 가 아직 안 잡힌다.

## 8. 분리가 어택을 얼마나 지우는가 — 처음으로 직접 쟀다 (2026-08-19)

지금까지의 정답지는 전부 이미 분리된 스템(`bass_sample.wav` 등)에서 나왔다. 그래서 "놓친 음이
분리 때문인지 검출기 때문인지"를 가를 방법이 없었다 — 다음 과제 1번, 아직 안 해본 것 3번이
그래서 남아 있었다. 이번에 실제로 만들었다.

**방법**(`npm run lab -- synth` → `synth-mix` 또는 `synth-mix-real` → `sepattack[-real]`):

1. `synth.js` 로 시각·음정을 우리가 정한 합성 베이스(`bass.wav`, 156음)를 만든다 — 기존과 동일.
2. 거기에 배경을 더해 `mix.wav` 를 만든다. 두 버전을 만들어 같이 잰다:
   - `synth-mix.js` — 드럼·패드를 Karplus-Strong·사인파로 지어낸다(약함, 아래에서 이유가 나온다).
   - `synth-mix-real.js` — **진짜** 드럼·기타·보컬 스템(`manifest.json` 의 첫사랑 샘플, 이미
     분리해 둔 것)을 얹는다(강함).
3. `sepattack.html` 이 `mix.wav` 를 **실제 제품과 같은 htdemucs(4-stem) 로 분리**하고, 나온
   베이스 스템을 원본 `bass.wav` 와 같은 시각에서 견준다 — 정답을 우리가 정했으므로 가능하다.

**잡아낸 방법론적 함정 — 정규화 배율.** 클리핑을 피하려고 믹스 전체를 한 번 더 정규화하는데
(`g = 0.73~0.79`), 그 배율만큼 베이스도 이미 작아진 채로 믹스에 들어간다. 처음엔 원본
`bass.wav`(정규화 전 진폭)와 분리된 스템을 직접 견줘서 "손실"을 쟀는데, 그중 상당 부분이
**내 정규화 자체**였다. `bass-as-mixed.wav`(= 베이스 파트 × g, 완벽한 분리기라면 그대로
나와야 하는 파형)를 따로 저장해 기준을 바꾸니 손실 수치가 달라졌다 — 이 프로젝트가 세 번째로
잡아낸 "잣대를 안 재고 결과를 읽은" 사례다(위 "6. 여기서 배운 것" 참고). 지금 코드는 고쳐져 있다.

**결과 (73초 · 156음, 20ms 창 RMS 비율 = 분리 후 / 분리 전)**:

```
                    채보 점수(천장→실전)          어택 에너지 생존율(중앙값 · 50%+손실)
지어낸 배경(약함)    81% → 18%(잉여 190)          전체 0.25배 · 78%   반복 0.19배·89%  새음 0.31배·62%
진짜 배경(강함)      81% → 52%(잉여 91)           전체 0.15배 · 100%  반복 0.17배·100% 새음 0.13배·100%
```

**읽는 법**:

- **지어낸 배경은 못 믿는다.** 채보 점수가 18%까지 떨어지고 잉여가 190개(검출 313개 중) —
  실제 곡 스템에서 본 어떤 수치보다도 나쁘다. Karplus-Strong·사인파가 htdemucs 에게
  "악기처럼 안 보이는" 신호라서 분리 자체가 비정상으로 나빠졌을 가능성이 크다. 반복/새음
  격차(0.19 vs 0.31)도 이 비정상성의 산물일 수 있어 그대로 믿지 않는다.
- **진짜 배경이 신뢰할 값이다.** 채보 52% · 잉여 91 — 실제 곡 스템(84~89%대)보다는 낮지만
  같은 자릿수라 분리 자체는 정상으로 작동했다고 본다. 여기서는 **반복 타현과 새 음의 어택
  손실이 사실상 같다**(0.17 vs 0.13, 둘 다 100% 가 절반 이상 잃는다) — 지어낸 배경에서 보였던
  격차가 재현되지 않았다. 즉 **"반복 타현이 유독 놓친다"는 실패 모드는 어택 에너지가
  차별적으로 지워져서가 아니다.** 에너지는 반복이든 새 음이든 거의 다 지워진다.
- 그런데도 채보는 52%를 맞춘다 — 온셋의 100%가 "50% 이상" 에너지를 잃었다고 해서 전부
  놓치는 건 아니라는 뜻이다. 남은 신호가 문턱을 넘기만 하면 잡힌다. 그래서 **원인은 에너지
  손실량 자체가 아니라, 그 손실 후에도 온셋 문턱을 넘는지(SNR)** 에 있을 가능성이 높다 —
  다음에 잴 것은 절대 에너지 비율이 아니라 "손실 후 국소 잡음 대비 몇 배인가"다.
- **잉여(오검출)가 이 실험에서 가장 크게 튀는 수치다.** 실제 곡 스템에서 본 잉여(26~117,
  580~693음 중)보다 밀도가 훨씬 높다(91개, 156음 중). 이게 내 믹스가 베이스를 상대적으로
  더 크게 넣어서(다른 세 파트와 RMS 를 맞췄을 뿐 실제 마스터링 관행과 다를 수 있다) 새는
  소리가 더 잘 들리는 것인지, 아니면 진짜 흔한 현상인지는 아직 모른다 — 다음 실험감이다.

**남은 불확실성**: 곡 하나(진짜 배경도 결국 한 곡의 드럼·기타·보컬)에서 나온 결과다. 지어낸
배경이 정상 작동을 방해한다고 결론 내렸지만 다른 지어낸 배경(더 사실적인 드럼 샘플 등)으로도
같은지는 안 재봤다. 잉여가 왜 이렇게 높은지도 원인을 못 짚었다.

## 9. 잉여의 정체를 쫓았다 — 세 가지 특징 다 못 가른다 (2026-08-19)

8번의 "잉여 91개" 원인을 파고들었다. 순서대로:

1. **note.low(저역 에너지 비율, "누수 판별용" 주석까지 있는데 실제로 아무 데서도 안 읽던 값)를
   먼저 시험.** 진짜 음 중앙값 0.890, 잉여 중앙값 0.894 — **완전히 같다.** 문턱을 0.3~0.7
   어디에 그어도 잉여가 0% 제거된다. 딴 악기가 새어 들어와서 생긴 게 아니라는 뜻이다 — 새는
   거라면 저역 밖 에너지가 섞여 있어야 하는데, htdemucs 의 "베이스 스템" 마스크 자체가
   저역에만 반응하도록 학습됐으니 거기서 나오는 건 뭐든 저역일 수밖에 없다. 돌이켜보면
   당연한 결과였다.
2. **note.conf(YIN 확신도) · note.rms(세기)도 같이 시험.** 둘 다 약하게만 갈랐다
   (conf 0.8 문턱 — 제거 21% 대 피해 13%, rms 0.008 — 제거 32% 대 피해 15%). 쓸 만한
   분리선이 아니다.
3. **잉여가 "딴 소리"가 아니라 "쪼개진 진짜 음"인지 확인.** 잉여 91개 중 59개(65%)가 바로
   옆에 같은 음정의 "진짜" 음을 두고 있었다 — 별개의 오검출이 아니라 **한 음이 둘로
   잘린 것**이었다. 그중 46개(78%)는 간격이 45ms 이내(`opts.gapMs`) 라 `segment()` 의
   "같은 음이 짧게 끊기면 잇는다" 병합 규칙에 걸렸어야 했는데 안 걸렸다 — 남은 원인은 그
   사이에 온셋이 잘못 잡혀 병합을 막은 것뿐이다.

**시도한 고침**: `detectOnsets()` 가 이제 온셋 여부(`onset`)뿐 아니라 문턱을 얼마나
넘었는지(`margin` = flux − bar)도 함께 반환하고, `segment()` 의 같은-음정 병합 판단이
새 옵션 `mergeOnsetMargin`(기본 0 = 예전과 동일)만큼 margin 이 커야만 "진짜 재타현"으로
쳐서 병합을 막도록 바꿨다. 애매하게 문턱을 겨우 넘긴 온셋(분리 노이즈로 추정)은 더 이상
병합을 막지 않게 하려는 것.

**결과 — 깔끔한 승리가 아니었다** (`npm run lab -- sepattack-real`, mergeOnsetMargin 훑기):

```
margin   검출   일치(%)   음정오류  놓침  잉여
0        192    81(52%)   20        55    91
0.05     163    74(47%)   20        62    69
0.12     135    71(46%)   18        67    46
0.25     115    65(42%)   16        75    34
0.35     111    63(40%)   17        76    31
```

margin 을 올릴수록 잉여는 줄지만(91→31) 일치도 같이 준다(81→63) — **거의 비례해서
같이 빠진다.** 뚜렷한 무릎(잉여만 뚝 떨어지고 일치는 그대로인 지점)이 없다. 놓침이 동시에
느는 것(55→76)이 이유를 말해준다 — margin 을 올리면 진짜 빠른 반복 타현(정답지 안에도
있다)까지 "약한 재타현"으로 오인해 하나로 합쳐버린다. 즉 **분리 후에는 노이즈로 인한
가짜 재타현과 진짜 재타현이 flux margin 하나로 안 갈린다** — 둘 다 에너지가 거의 다
지워진 채로(8번 결과) 남은 잔여물이라, 이 축 위에서 뭉쳐 있다.

**그래서 low·conf·rms·onset-margin 네 가지 특징 전부 실패했다.** 이 파이프라인이 지금
프레임·노트 단위로 계산하는 어떤 스칼라 값으로도 "진짜 쪼개진 음"과 "가짜 재타현"이
안 갈린다는 뜻이다. 코드는 남긴다(`mergeOnsetMargin` 기본값 0 이라 동작은 그대로다) —
당장 쓸모는 없지만 다음 시도가 margin 자체를 재사용할 수 있고, `onsetAdaptive` 처럼
"해봤고 아니었다"의 증거로도 값어치가 있다.

**다음으로 볼 만한 것**: 지금까지 특징은 전부 베이스 스템 **안에서만** 났다. 아직 안 본
것 — 같은 순간 **다른 스템(드럼·기타·보컬)에도 에너지가 같이 튀는가.** 진짜 재타현은
베이스 혼자 튀고, 분리 아티팩트는 원래 거기 있던 다른 악기의 잔향/누수일 가능성이 있어
그 스템에도 흔적이 남을 수 있다 — sepattack.html 이 stems 전체(`drums`·`other`·`vocals`)를
이미 갖고 있으니 추가 분리 없이 바로 시험 가능하다.

### 다섯 번째도 실패 — 다른 악기 활동과도 안 갈린다

원본(분리 전) 드럼·기타류·보컬 중 그 순간 최댓값 활동을 재서 견줬다(`sepattack-real`,
synth-mix-real.js 가 애초에 믹스에 넣었던 파일과 직접 비교 — 분리를 한 번 더 안 한다).

```
진짜 101개 중앙값 0.1577 · 잉여 91개 중앙값 0.1617
```

**진짜와 잉여가 사실상 같고, 오히려 진짜 쪽이 살짝 낮다** — 누수 가설과 반대 방향이다.
문턱을 걸면 low·conf·rms·margin 과 똑같은 모양이 나온다(제거율과 피해율이 거의 비례해서
같이 움직인다, 0.01~0.04 구간은 아예 100%/99% — 곡에 드럼·보컬이 거의 항상 깔려 있어서
"다른 악기가 그 순간 활동했는가"는 거의 항상 참이다). 진짜 재타현이 다른 악기가 조용할
때만 일어나는 게 아니므로 이 신호도 무의미했다.

**다섯 가지(low·conf·rms·onset-margin·다른-스템-활동)를 전부 재고 전부 실패했다.** 이 정도로
넓게, 매번 같은 모양(제거율≈피해율, 뚜렷한 무릎 없음)으로 실패하는 건 우연이 아니라 —
지금 파이프라인이 프레임·노트 단위로 계산하는 **어떤 스칼라 값으로도 이 둘이 안 갈린다**는
신호로 받아들여야 한다. 다음 후보는 더 넓은 문맥을 보는 방법(작은 분류기를 학습시키거나,
스펙트럼 모양 전체를 보거나)이거나, 아예 다른 접근(pYIN/CREPE 로 검출 자체를 바꾸기)이지,
지금과 같은 "특징 하나 더 재보기"는 아닐 가능성이 높다.

## 10. pYIN — 깨끗한 신호에선 이겼는데 분리를 거치면 진다 (2026-08-19)

프레임마다 하나를 그 자리에서 확정하는 YIN 대신, CMND 국소최소를 최대 3개(+옥타브 위·아래
대안 각 1개, 최대 9개) 후보로 남기고 전체 곡에 대해 Viterbi 로 가장 매끄러운 피치 경로 하나를
고르는 방식을 넣었다(`tab-core.js` 의 `pyinFrameCandidates`/`pyinViterbi`, `opts.pitchTracker:
'pyin'` — 기본은 여전히 `'yin'`). 상태는 반음을 5등분한 격자 + 무성음, 비용은 확률이 아니라
`assignFrets()` 의 DP 와 같은 관용구(작을수록 좋음)로 잰다.

**처음 버전은 실제 곡(210초)에서 30분을 넘겨도 안 끝났다.** 원인은 bin(약 280개)마다 emitCost 를
부르면서 그 안에서 후보의 hz→미디 변환을 매번 다시 계산하고 있었던 것 — bin 과 무관한 값을
280배 낭비해서 재고 있었다. 후보의 미디값은 프레임당 한 번만 구해 두고, `cur`/`backtrack` 버퍼도
프레임마다 새로 만들지 않고 미리 잡아 둔 자리를 재사용하도록(`yinFrame()` 의 scratch 와 같은
관용구) 고치니 210초 곡의 Viterbi 가 **7.9초**로 끝났다. (오래 걸리는 걸 분리 실험과 동시에 돌려서
"멈췄나" 착각하기도 했다 — 두 개의 무거운 Electron 프로세스가 CPU 를 나눠 쓰면 각자 몇 배씩
느려진다. 오래 걸리는 도구는 하나씩 돌릴 것.)

**결과 — 깨끗한 신호(합성 베이스, 분리 전)에서는 명확히 이긴다.** 튜닝 상수(SIGMA·NEAR_COST·
JUMP_COST·V2U·U2V·UNVOICED_EMIT) 하나도 안 만지고 첫 시도:

```
              검출   일치(%)      음정오류  놓침  잉여
YIN           152    126(81%)     17        13    9
pYIN          147    129(83%)     15        12    3
```

전 항목 개선, 잉여는 3분의 1. `npm run lab -- synth-score` 로 재현된다.

**그런데 분리를 거치면(`sepattack-real`, 이번 세션의 진짜 잣대) 진다.**

```
                    검출   일치(%)      음정오류  놓침  잉여
YIN 분리전(천장)     152    126(81%)     17        13    9
pYIN 분리전(천장)    147    129(83%)     15        12    3
YIN 분리후(실전)     192     81(52%)     20        55    91
pYIN 분리후(실전)    182     72(46%)     27        57    83
```

같은 오디오, 같은 정답지 — 분리를 거쳤는가만 다른데 결과가 뒤집힌다. 잉여는 8개 줄었지만
(91→83, 9번 절의 다섯 특징보다는 낫다) 일치가 9개 줄고 음정오류가 7개 늘어 전체는 손해다.

**왜 뒤집히는지는 8·9번과 같은 이야기다.** 분리 후엔 온셋의 100%가 에너지 절반 이상을 잃고,
진짜 재타현과 잡음이 이 세션에서 시험한 어떤 특징으로도 안 갈린다. Viterbi 는 "전체 흐름에서
가장 매끄러운 경로"를 고르도록 설계했는데, 분리 잡음이 우연히 그 나름대로 매끄러운(그러나
틀린) 대안 경로를 만들면 Viterbi 는 YIN 의 프레임별 하드 결정보다 **더 확신을 갖고 그 틀린
경로에 안착한다** — 매끄러움을 상으로 주는 설계가 매끄러운 잡음에도 상을 준 것이다. 중앙값
필터(옛 방식)는 지역적 이상치 제거라 이런 전역적으로 일관된 오류에는 오히려 덜 낚인다.

**튜닝을 전혀 안 했다는 점은 남겨 둔다.** SIGMA·JUMP_COST 등 여섯 상수는 전부 첫 감으로 정한
값이고, 분리 후 조건에 맞춰 다시 골라 본 적이 없다 — `octUpRatio`/`octUpH2` 가 두 곡 격자 훑기로
자리를 잡았던 것처럼, 이 여섯 상수도 `sepattack-real` 을 기준으로 훑으면 지금 지는 폭이 줄거나
뒤집힐 수 있다. 안 해본 것이지, 안 되는 것으로 확정된 것은 아니다.

**기본값은 그대로 `'yin'` 이다.** 이 옵션은 `pitchTracker: 'pyin'` 을 명시해야만 켜진다 — 지금
상태로 기본을 바꾸면 실전 조건에서 후퇴다.

## 11. CREPE — 이번 세션 처음으로 분리 전·후 둘 다 이겼다 (2026-08-19)

pYIN 은 깨끗한 신호에서 이기고 분리 후엔 졌다(10번). 다음 후보로 신경망 단선율 f0 모델
CREPE(marl/crepe, MIT)를 붙였다 — 다른 실패 모드를 가질 수 있다는 게 애초의 기대였다.

**모델 확보.** marl/crepe 는 공식 ONNX 내보내기가 아직 main 에 머지되지 않아서(PR #105,
2025-04 오픈·미병합) 이미 배포된 pip 패키지(`pip install crepe`)의 Keras 가중치를
`lab/tab/tools/crepe_to_onnx.py` 로 직접 tf2onnx 변환했다. 순음(41.2~440Hz) 검증으로
변환 정확도를 확인했다(수 cent 오차). 출처·라이선스는 `renderer/models/NOTICE.md`.

**용량 — tiny 는 베이스 저음에서 못 쓴다.** 처음엔 빠른 tiny(2MB)로 돌렸는데 클린 신호에서도
26%(옥타브무시 32%)로 YIN·pYIN 에 크게 밀렸다. 공식 파이썬 구현(`crepe.predict`)으로 직접
검증하니 내 통합 문제가 아니었다 — 합성 베이스 E1(41Hz) 구간에서 tiny 는 confidence
0.1~0.3 에 287Hz(엉뚱한 배음)로 튀고, full 은 같은 구간 confidence 0.87~0.93 에
41.2~41.4Hz 로 정확했다. tiny 는 애초에 이 음역을 감당 못 한다 — full 로 바꿨다.

**통합 방식.** ONNX 추론이 비동기라 `transcribe()` 를 바꾸지 않고 별도의
`transcribeCrepe(salience, hopSec, mono, sampleRate, opts)` 를 새로 만들었다(순수 함수 —
추론은 `crepe-run.js` 가 맡는다). CREPE 의 360bin 살리언스에서 상위 K개 국소 피크를 뽑아
pYIN 이 이미 쓰던 `pyinViterbi()` 에 그대로 넣는다 — CREPE 자신의 공식 구현도 Viterbi
평활(`to_viterbi_cents`, hmmlearn)을 권장 옵션으로 두고 있어 같은 방향이다. 온셋·분절·
테크닉·운지는 YIN/pYIN 과 완전히 같은 코드(`finishFromPitchTrack()`)를 탄다.

**배치 추론과 속도 — 여기서 한참 헤맸다.** 프레임 하나씩 session.run() 을 부르면(첫 버전)
73초 곡 하나에 7000번 넘게 WASM 을 넘나들어 그 호출 오버헤드가 실제 연산보다 커졌다 —
marl/crepe 자신도 `model.predict(frames,...)` 로 배치를 한 번에 돌린다. ONNX 로 내보낼 때
배치 축을 동적으로 뒀으므로(`crepe_to_onnx.py`) 64개씩 묶어 부르게 고쳤다.

그래도 CPU(WASM) 에서 full 은 배치당 5.4초 — 210초 곡 하나에 10분 넘게 걸렸다. 게다가
오프스크린 lab 하네스(`show:false, offscreen:true`) 안에서는 Chromium 이 백그라운드 창으로
보고 스케줄링을 크게 깎는지, 실측 배치가 몇 분씩 멎었다 풀렸다 했다(짧은 연산에선 안
드러나던 문제 — pYIN 의 Viterbi 도 처음엔 이걸로 "멈췄나" 착각했다, 실제로는 그냥 느렸을
뿐이었다). 사용자 컴퓨터의 다른 백그라운드 앱(게임 런처 등)을 끄니 일부 나아졌지만
근본 원인은 아니었다.

**해법은 WebGPU 였다.** `separator.js`/`stem-worker.js` 가 htdemucs 분리에 이미 쓰는 것과
같은 방식 — `navigator.gpu.requestAdapter()` 로 확인하고 되면 `executionProviders:
['webgpu']`, 안 되거나 실패하면 WASM 으로 자동 전환(`crepe-run.js` 의 `ensureSession`).
그런데 `scripts/lab.js` 의 오프스크린 드라이버가 `app.disableHardwareAcceleration()` 을
불러서 WebGPU 자체가 원천 차단돼 있었다 — 지웠다(다른 lab 도구는 렌더링을 안 쓰니 영향
없다. sepattack 의 htdemucs 분리는 결정론 때문에 여전히 WASM 을 못박아 둔다 — 그쪽은
그대로 느리다). 결과: **CPU 배치당 5.4초 → GPU 로 5초 오디오 전체가 1.81초.** 73초 곡
전체가 12.1초로 끝났다.

**결과 — 클린 신호, 분리 후 둘 다 CREPE 가 이긴다.**

```
                    검출   일치(%)      음정오류  놓침  잉여
YIN  분리전(천장)    152    126(81%)     17       13    9
pYIN 분리전(천장)    147    129(83%)     15       12    3
CREPE분리전(천장)    151    135(87%)      6       15   10

YIN  분리후(실전)    192     81(52%)     20       55   91
pYIN 분리후(실전)    182     72(46%)     27       57   83
CREPE분리후(실전)    169     85(54%)     14       57   70
```

pYIN 은 클린에서만 이기고 분리 후엔 졌다(10번). **CREPE 는 두 조건 다 YIN 을 이긴다** —
분리 후 일치 54%(YIN 52%) · 음정오류 14(YIN 20·pYIN 27, 가장 적다) · 잉여 70(셋 중 가장
적다). 놓침만 YIN(55)보다 조금 많다(57, pYIN 과 동률).

**아직 안 한 것**: `topKCandidatesFromSalience` 의 K 나 pyinViterbi 상수는 pYIN 때와
마찬가지로 튜닝 전 값 그대로다 — 이미 이기고 있으니 급하지 않지만, 놓침이 YIN 보다 많은
이유가 그 상수 탓인지는 재보지 않았다. `pitchTracker`/`transcribeCrepe` 는 여전히 옵트인이고
기본은 `'yin'` 이다 — 이번 결과가 좋다고 여기서 바로 기본을 바꾸지 않는다. 두 번째 곡(다음
과제 참고)에서도 같은 우위인지가 다음 확인 대상이다.

## 12. 코드 성질(장·단·sus4·sus2·…) — 근음 고정 스코어러를 처음으로 직접 쟀다 (2026-08-21)

베이스 TAB 화면에 마디마다 코드를 얹는 기능(tab-chord.js `chordQualityAt`, tab-score.js
`computeBarChords`)을 붙였는데, 실사용(버스커 버스커 "첫사랑")에서 정확도가 안 맞다는
제보가 반복됐다. 그때그때 추론으로(보컬 빼라, confidence 넣어라) 고쳤는데 — 사용자가
정확히 짚었다: "니가 제공해줘서 해결되는 건 의미 없다, 오로지 코드로만 정확도가 높게
도출되어야 한다." 지금까지 한 번도 정답을 아는 오디오로 재본 적이 없었다. `synth.js`
(베이스 온셋·음정용)와 같은 방법으로 `chord-synth.js` 를 만들었다 — 근음·성질을 우리가
정해서 화음을 합성하므로 검출기와 무관한 정답이 나온다.

**방법**: `chordQualityAt(mixMono, sr, t0, t1, rootPc)` 는 근음(rootPc)을 이미 안다는
전제로(베이스가 알려준다) 그 자리에서 성질만 후보 중 크로마로 고른다. 근음은 정답으로
주고 성질 판정만 쟀다 — 근음 자체가 맞는지는 베이스 검출(이미 따로 검증됨) 영역이라 이
실험 범위 밖이다. 세 조건으로 스트레스를 줬다: 클린(순정 3화음), add9(9음 얹은 실전
보이싱 흉내), bleed(화성 스템에 낮은 레벨 브로드밴드 잡음 — 분리가 완벽하지 않은 것 흉내).

**1차 결과 — 장·단·sus4 만(기존 후보)**: 세 조건 다 100%. 파워코드(근음+5도만, 정답
없음)는 confidence 0.02~0.07 로 낮게 나와 조성표 폴백이 제대로 걸렸다. 여기까진 지금
쓰는 로직이 맞았다는 뜻 — 사용자 제보(Fm7→F, F-G-Em-Am 오검출)의 원인은 성질 판정이
아니라 근음 자체나 마디 경계 쪽일 가능성이 크다는 결론이었다.

**사용자가 다시 밀어붙였다**: "sus4만 재는 게 아니라... 존재하는 모든 스케일을 다 감지할
수 있어야지." 그래서 후보를 9종(장·단·sus4·sus2·dim·aug·7·maj7·m7)으로 늘려 같은 세
조건으로 다시 쟀다:

| 성질 | 클린 | add9 | bleed |
|---|---|---|---|
| 장/단/sus4/sus2 | 91~100% | 75~100% | 83~100% |
| dim/aug | 67~83% | 75~83% | 67~83% |
| 7/maj7/m7 | 33~75% | 25~58% | 33~67% |

**걱정했던 것과 실제로 벌어진 것이 반대였다.** 예전 주석은 "7화음이 3화음의 상위집합이라
애매할 때마다 이겨서 뺐다"(자유 근음 탐색 얘기)였는데, 근음을 고정한 이 스코어러에서는
정반대로 7화음·dim·aug 가 과소검출돼 자꾸 단순 3화음으로 뭉개졌다(`C7→C`, `Dm7→Dm`,
`Cmaj7→C`). "다 잡자"고 후보를 늘렸다가 확신 있게 틀린 라벨만 늘어난 셈이다.

**결론 — sus2 만 추가, 나머지는 보류**: sus2 는 세 조건 다 83~100%로 안정적이라 넣었다.
dim·aug·7·maj7·m7 은 정확도가 못 미더워 뺐다. 이건 게으름이 아니라 원리적 한계와도
맞물린다 — 9/11/13도·변화화음처럼 크로마(12 피치클래스) 하나로 못 가르는 화음이 실제로
있고(같은 피치클래스 집합이 여러 이름과 겹친다), 7화음처럼 원리적으로는 갈리는데 이

추정하는 기능은 없다 — 코드 성질 확장과는 다른 작업이라 이번엔 손대지 않았다.

## 다음 과제

- **손 정답지의 50ms 밀림.** 상수라 채점에서는 걷어내지만, 표기 도구가 파형 위에 검출된
  에너지 상승 지점을 흐리게 겹쳐 보여주면(정답으로 쓰지 않고 눈금으로만) 다음 표기는 더 정확해진다.
- **두 번째 곡.** 지금 판정은 전부 한 곡에서 나왔다. `onsetWinMs: 20` 이 이 곡의 습관인지
  아닌지는 다른 곡에 대고 재봐야 안다. (8번의 분리 실험도 같은 제약 — 배경 곡을 하나 더 대야 한다.)
- **손실 후 SNR로 재보기.** 8번에서 나온 다음 질문 — 20ms 창의 절대 에너지 비율이 아니라
  "분리 후 그 구간 에너지가 바로 그 자리의 국소 잡음(무음 구간·인접 프레임)보다 몇 배인가"를
  재면, 검출기가 실제로 무엇을 기준으로 살아남는지가 잡힐 것이다.
- **잉여(오검출) 폭증의 원인.** 진짜 배경 실험에서 잉여가 91/156으로 실제 곡보다 훨씬 높았다.
  믹스 밸런스(베이스가 상대적으로 큼) 탓인지 분리 자체의 특성인지 갈라야 한다 — 베이스 레벨을
  낮춰 다시 섞고 재보는 것이 가장 빠른 다음 수다.
- **pYIN 상수를 `sepattack-real` 기준으로 훑기.** 10번 — 지금 SIGMA·JUMP_COST 등은 튜닝 전
  첫 감이다. 분리 후 조건에서 졌다는 것과 "이 여섯 상수로는 못 이긴다"는 것은 다른 말이다 —
  둘 다 조건에 넣고 격자 훑기 전에는 어느 쪽인지 모른다.
- **CREPE 를 두 번째 곡·`mergeOnsetMargin`·`sameStringPenalty` 등과 같이 재기.** 11번에서
  YIN 을 이겼지만 아직 한 곡·튜닝 전 상수뿐이다. `topKCandidatesFromSalience` 의 K 를
  바꾸면 놓침(57)이 줄어드는지, 실제 배포 전에 확인이 필요하다.
- **7화음 스코어링 공식 다듬기.** 12번 — dim/aug/7/maj7/m7 이 과소검출되는 게 원리적
  한계인지 지금 `scoreOneState`(in-set/out-set 평균)의 약점인지 안 갈랐다. 7음 존재를
  별도 이진 판정(있다/없다)으로 분리하거나 템플릿별 가중치를 주는 식으로 다시 시도해
  볼 만하다 — `chord-synth.js` 로 바로 재볼 수 있다.
- **분리도 WebGPU 로 — 결정론과 맞바꿀 가치가 있는지.** 11번에서 CREPE 는 WebGPU 로
  23배 빨라졌는데 sepattack 의 htdemucs 분리는 여전히 WASM 고정이라(재현성 때문에
  일부러 그렇게 뒀다) 이 환경에서 오프스크린 창 스로틀링에 계속 걸린다. WebGPU 는
  가끔 NaN 이 나와 재시도가 필요하다(separator.js 의 기존 처리) — 그 비결정성을
  감수할 가치가 있는지는 아직 안 재봤다.
